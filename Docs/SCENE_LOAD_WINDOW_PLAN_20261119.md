### 快取冷暖要进趟的身分

**同一个执行档上的冷趟与暖趟不是同一个实验。** E 组刚量到同一执行档上 shader 关联时间差约 100 倍
（11 ms 对 1008 ms）；而 shader 编译与 DDC 命中正是**场景载入耗时里最大的变数之一**，
第一次开某个场景和第二次开的差距**可能大过我要量的那个旋钮**。所以每趟的结果行都要写上：

- **这个场景在这次窗口里是第几次开**（第 1 次＝冷）；
- shader 编译相关的时间栏位（有的话）；
- **DDC 是否刚清过**。

判读规则两条：
- **交错两轮保留，并且要让 0 和 1 各有一趟落在前半、一趟落在后半**（四趟交错正好满足）；
  **绝不拿「第一趟 vs 第二趟」去比** —— Q1 的第一趟很可能是整段里最冷的那趟。
- **某趟明显偏离同设定的另一趟时，先怀疑冷暖，不是先怀疑旋钮。**
- Q2 同理：`build_frames` 的推进速率在冷快取下会被 shader 编译拖慢，
  **截断那一行要连快取状态一起写**，否则「到上限还没开完」分不清是慢、是卡住、还是在编 shader。

**`--purpose load`，不是 `shots`**：载入耗时吃语音档，音档要算进指纹。比之前先 `check`，
**只有 exit 0 可比**（1 DIFFERENT／2 MISSING／3 OLD 或 RULES），**别接管线**（`$?` 会读到管线最后那个指令的码）。

## Q1：`ok.Studio.SyncFindIndex` 的预设该是 0 还是 1？

**为什么值得量**：它**现在预设是 1**。如果 1 真的比 0 慢，我们一直在出比较慢的预设——
这个答案会直接改变一行程式（翻预设）。先前那组量到 `ready_ms` **+24.7%**（索引开反而更慢），
但那组是各一趟、执行档含未提交的计数器、而且没有阳性样本，已经降级为**不可判**
（见 [OK_STUDIO_SCENE_LOAD_PERF_20261117.md](OK_STUDIO_SCENE_LOAD_PERF_20261117.md) 的自查节）。

- **最小实验**：`koikatu_cs0003420_2.okscene`（8 806 物件），`SyncFindIndex` 0／1 交错两轮，共 4 趟。
- **阳性样本（独立于被判的指标）：`find_index_builds`。** 不是 `sync_world_ms`。
  这是**开跑前读程式码确定的**（7f）：`SyncFindIndex=1` 让 `FFindScope` 开着，
  `Find(Id)` 走雜湊索引（每个 scope 第一次查就建一次，计数器 `FindIndexBuilds()`）；
  设 0 则 scope 是空的，`Find` 退回 `FindByPredicate` 线性扫描。**两条路都在同一段里付钱**
  （`WorldTransform` 就在 `sync_world_ms` 的窗口内），所以**不会有「工作搬到别的阶段」这回事**——
  能分辨两条路的是**索引建了几次**，而它已经写进 profile：`find_index_builds`
  （`OKStudioLoadProfile.cpp:223`）。实测一趟预设（cvar=1）是 **4149**。

  **开跑前写下的预测（到达）**：设 1 → `find_index_builds` **远大于 0**（千的量级，随 Sync 次数走）；
  设 0 → **恰好 0**。
- **开跑前写下的预测（效果的方向与量级）**：设 0 走线性扫描，所以 **`sync_world_ms` 应该比设 1 慢**
  （索引是为了省时间才加的）。三种结果事前都有名字：
  **慢了**＝索引有用、预设 1 正确；**一样**＝这段本来就便宜（第 10 条措辞）；
  **设 0 反而更快**＝索引在这个场景规模上得不偿失、**预设该改 0**——那不是「cvar 没效果」，
  是需要解释的结果（建索引的成本高过它省下的查找成本），而且**是这题最有行动价值的那个发现**。
- **每趟都记 `find_index_builds`**，不只拿来判到达：若设 1 的三趟之间它也在跳，
  说明场景载入本身有随机性，那是解读秒数散布时必须知道的事。
- **旋钮输入盘点（第 7 条的操作化，开跑前做完）**：能设定这个旋钮的输入只有两个，都已控制——
  cvar `ok.Studio.SyncFindIndex`（预设 1，`OKSceneActor.cpp:574`）与环境变数 `OK_STUDIO_FIND_INDEX`
  （`OKSceneDocument.cpp:127`，**=0 时盖过 cvar**）。查过了：`Config/*.ini` 没有任何 `ok.Studio` 设定，
  `Saved/Config` 没有它，使用者层与机器层的环境变数都没有，启动脚本也没有带。
  runner 仍然明确把那个环境变数清掉——**不是因为现在有，而是因为它若出现就无声地毁掉整题**。
- **一趟算不算完成，由程序判定（不是由数字判定）**：runner 在趟末检查
  `sync_world_ms`、`find_index_builds`、`ready_ms` **三栏齐全**才算这趟成立；缺任何一栏就作废**并记明缺哪一栏**
  （7g：缺资料判失败，不能拿 0 去填）。这是依程序剔除，合规；依结果剔除（数字不合意就重跑）不合规。
- **`find_index_builds` 同时是这一段的「批内存活对照」**：它跨设定必然变化（数千 → 0），
  所以它变了就证明**整条链当下是通的**——引擎、cvar 路径、profile 写出、我的解析，
  不只是「有行程」或「有执行绪答话」。因此 **`FAILED-knob-did-not-arrive` 触发时，
  同一段里之前那几趟的数字也要一起标可疑**（它们可能是上一趟留下的或半完成的），
  不要只作废当前这趟。
- **挂钟上限**：runner 第四个参数，预设 600 秒，超时自己收掉并标记。
  **不要用「游戏 MCP 还答得出话」判断一趟还活着**——`OKControl` 在独立执行绪，
  **算绘装置死了它照样回应**；真正的死讯是 crash reporter 行程出现、或 log 的时戳不再前进、
  或上面那三栏没写出来。
- **判读三分，每一种都明确（不依结果剔除趟）**：
  | 看到 | 读成 | 接下来 |
  |---|---|---|
  | 设 0 时 `find_index_builds` = 0、设 1 时 ≫ 0 | **旋钮到达了** | 才去比 `sync_world_ms`／`ready_ms` |
  | 设 0 时它仍 > 0 | **旋钮没到达**（第 1 种） | **停下来查接线**，不是重跑；先查 `OK_STUDIO_FIND_INDEX` 这个环境变数（它会盖过 cvar） |
  | 到达了但 `sync_world_ms` 没差 | **到达了、这段工作本来就便宜** | 结论写「这个 cvar 在这两个场景上不改变载入耗时」（第 10 条措辞） |

  **不得因为「数字没差」就作废一趟重跑**：那是依结果剔除，重跑到有差为止必然有差；
  而且重跑解决不了歧义——歧义要用独立的到达证据解，不是用更多趟。
- **判准：用 `sync_world_ms`，不用 `ready_ms` 下结论。** 自测那两趟给了理由：`ready_ms` 的趟间抖动
  **大于 1.7 秒**（38.1 对 39.7，而且注入 2 秒的那趟反而比较小）——**一个 2 秒的真实变化在 `ready_ms`
  上看不出来**。38 秒的载入上，1.7 秒是 4.5%：**任何小于约 5% 的端到端效果，用 `ready_ms` 这把尺看不见**，
  会把「判不出来」写成「没效果」。`ready_ms` 照记，但只有效果明显超过它自己的地板时才拿来下结论。
- **开跑前先量 `sync_world_ms` 自己的地板**（第 11 条）：同设定连跑两趟，差值就是地板；
  0 与 1 的差没有明显大于它就写「**判不出来**」。这两趟并进交错两轮里，不另外花趟数。
  **地板用 `sync_world_ms` 量，不是 `ready_ms`**（后者自己的抖动就超过 1.7 秒）。
  **runner 冻结**：`scratchpad/q1_trip.lua`，`git hash-object` **95a6eacef1bd31c761625830e10914086e2e409a**
  （记进段 A 的纪录；它在 scratchpad 所以手动记）。它清掉 `OK_SELFTEST_SYNC_WORLD_SLEEP_MS`
  与 `OK_STUDIO_FIND_INDEX`，并在设 cvar 后回显一次（只排除打错名字，不当阳性样本）。
  **按 11d 检查这个地板，但要有第三趟**：「每次都是同一个数」在 n=2 看不出来——
  **两次相同是很常见的巧合**（尤其数值已被四舍五入）。所以**每个设定跑三趟**，
  同设定两两之差若都一样才谈系统性偏移；只有两趟就记「**n=2，分不出**」，

## Q2：`BuildsPerFrame` 512／`BuildSliceMs` 2000 会不会根本开不完？

**为什么值得量**：先前有**一趟跑了 16 分钟还没开完**（基线 139 s），被 slot 到期中止，没有数字，
原因未查。那不是「慢一点」，是**可能有 bug**（例如每帧预算大到让某个 O(物件×帧) 的东西退化，或根本卡住）。
这个答案会改变我们要不要给这两个旋钮设护栏、要不要去查那个退化。

- **最小实验**：同一张场景，`96/250`（现行）与 `512/2000` 各一趟，**各给 10 分钟上限**。
- **阳性样本**：`build_frames`。预算加大 → 帧数该明显变少；**帧数没变就是旋钮没生效**。
- **判准**：
  - 两趟都开完 → 比 `ready_ms` 与 `build_frames`，但**只报原始值与 n=1**，不报百分比。
  - `512/2000` 又没开完 → **这就是答案**：复现了，记成 bug 去查（日志停在哪一行、`build_frames` 卡在多少）。
  - **跑到 10 分钟上限的那一趟是截断观测**：标成截断，**不与开完的那趟一起算任何平均或最大值**。

**截断那一行要带速率**，否则「开不完」和「只是慢」分不开，而这两者后面要查的东西完全不同：
到上限时记下 **`build_frames` 还在不在上升**，以及**最近一分钟推进了多少**（帧数与已建物件数各记一个）。

| 到上限时看到 | 读成 | 接下来 |
|---|---|---|
| 还在稳定推进 | **只是慢** | 效能问题，比吞吐量 |
| 已经不动或趋近于零 | **卡住** | **是 bug 不是效能**，去查停在哪一行（日志最后一条、`build_frames` 卡在多少） |

所以那一行写成「截断于 10 分，`build_frames` N，最近一分钟 +M，**第几次开／shader 时间**」，
不要只写「到上限」—— 少了快取状态，「还在慢慢推进」分不清是慢、是卡住、还是在编 shader。
