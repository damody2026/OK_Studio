# 开卡性能优化（2026-11-17，E 树）

**使用者会感受到什么**（只看这两句就够）：
**打包版（只有 OK 卡）**——开第一张卡快约 0.4 s（1.52 → 1.27 s，−16.8%），之后每张只快一点
（四张合计 −2~5%），因为 OK 卡不读 mods 树，拿到的只有颜色遮罩那一项；读卡器启动后多花几百毫秒
在背景预热，换来第一张卡少付约 150 ms。**自己开原作卡（有遊戏目录与 mods）**——第一张差不多
（5.0 → 4.4 s），**但第二张之后快三到四成**（第二张 4.24 → 2.32 s、第三张 4.81 → 3.37 s），
也就是在读卡器里一张张翻卡的实际体验；另外把整个场景转成 OK 卡快约一成（21 角色 74 → 67 s）。

目标：让「开卡」（读卡器打开原作 KKS 卡与 OK 卡到可显示）实际变快。**前提：开卡的磁碟快取永久关闭**
（`70d8a21c7`，2026-10-28，多程序正确性；使用者 2026-11-17 再次确认「永远不要开开卡快取，想办法优化冷读取」），
所以**唯一的基准是「全新程序、无快取」的冷开**。

这份是独立的最终版，接手不必读任何对话。按时间顺序的过程记录（含被后续推翻的中间结论、各阶段的原始
分解数字）在 `Saved/Reports/card-open-perf-20261117/README.md`，**那是本机产物、不进版控**，可能被清掉；
需要长期保存的结论都在这份文件与 [ERROR_LOG.md](ERROR_LOG.md) 的 2026-11-17 各条里。

## 二、做了之后回退或放弃的（和收益一样重要，省掉重走一遍）

## 三、量测方法与陷阱

**方法（这台机器上唯一可信的做法）**

1. **只量冷开**：全新程序、无快取。磁碟快取永久关闭，所以没有「暖」这个基准。
   **而且要用读卡器自己的冷路径**：`ok-card-open-bench --sequence <库> <卡>` 搭配
   `OK_BENCH_PREWARM=concurrent`（启动预热跟第一张卡并行，就是 app 的样子）走 `open_card_like_reader`。
   **不要用 plain 模式**（`ok-card-open-bench <库> <卡>`）：它不跑预热，于是 `load_base_bundles` 与 `lists`
   会付 app 已经预热掉的成本，量出来的瓶颈位置是错的。11-18 的 hair gloss 那笔就是先在 plain 模式量了
   「零收益」，换到有代表性的路径才看清真正的原因（第二节）。plain 模式仍适合看**次数**类的指标。
2. **同一个执行档＋环境变数开关＋交错＋同时段＋取中位数**。不同次执行之间的差异不算 A/B。
3. **正确性用 `--fresh-dump` 逐位元组比对** session bytes（不是整档雜湊，见 ERROR_LOG I-014）：
   OK 卡 28 个 dump（C001／C006／C049／klara／C050／megumin，含 override 与眼睛贴图）＋原作卡 21 个。
4. 一切建置与量测**最多 8 执行绪**（`cargo -j 8`、`-MaxParallelActions=8`、`RAYON_NUM_THREADS=8`）。
4a. **A／B 两边必须同样的建置方式。** `Cargo.toml` 的 `[profile.release] incremental = true` 留着不关
   （增量重建对三组每天的建置时间有用），代价是 **codegen 自己就会漂约 4%**：六张 OK 卡交错三轮的中位数总和，
   改动前的二进位 5.30 s、当时那份 incremental 建置 5.70 s、**同一份程式码用 `CARGO_INCREMENTAL=0`
   全新建置 5.49 s**（2026-11-24，第十节）。所以要嘛两边都 incremental、要嘛两边都全新建，不然量到的是
   建置方式的差，不是改动的代价。`Tools/ok-extract/build-release.cmd`（Unreal 连结的那份 `ok_extract.lib`）
   也吃同一个 profile，所以这条对游戏里的时间一样成立。
4b. **`ok-card-open-bench` 的数字只代表 bench，不代表读卡器**（第三次踩到同一个教训，2026-11-24）。
   同一张卡（`Komazoku Megumin (2).png`）、**同一套服装（outfit 0）**、同一个庫、机器空着：
   bench `--sequence` **1.30 s**，读卡器 **3.0～4.1 s**（启动时第一次开 4.08 s，闲置后再开两次 3.02／2.99 s，
   所以不是启动争用）。两边 `OK_PROFILE` 的工作件数一样（`segment item decode 16x`），读卡器那边花在解码的
   CPU 还更少（845～919 ms vs bench 1680 ms，都是跨执行绪加总），时间却多两秒，而且都压在
   `clothes options`（1446 ms）与 `clothes renderer map`（1485 ms）上——bench 的整个 `clothes` 只有 140 ms。
   **所以读卡器那条路是在等，不是在多做**，还没定案等的是什么（装了 mod 的服装 bundle 的 I/O，还是 UE 行程里
   那两段没走到并行）。在定案之前：**基准表上的秒数要标明是 bench 的**，要谈使用者感受到的开卡时间就得量读卡器
   （`reader_launch` ＋ `OK_PROFILE=1`，取该卡第一笔 `extract_card_outfit TOTAL`；读卡器之后还会在背景把同一张卡
   再开 2～3 次做 clothing warm，后面那几笔不是同一回事）。

5. 会改变输出位元组的改动（例如缩小底图）**不适用**第 3 条，要改成目视＋平均 RGB 绝对差＋贴图记忆体。
6. **机器吵的时候改用确定性指标**：其他 session 同时在跑时，同一设定的冷开 wall 落在 1.46–2.79 s，
   100 ms 级的差异量不出来。`OK_PROFILE` 现在会印「这次开卡从零做了几件、其中几件是同一件做第二次」
   （`unity::take_work_counts`），这个数与机器忙不忙无关，可以在吵的机器上判断一个改动有没有真的少做事。
   **但它不能代替时间**：这一轮就有一笔「次数降了 6–7 次、时间反而慢 2.7%」（上一节最后一列）。
   次数用来**定位**，时间用来**定案**；时间要等得到一段安静，或者多轮交错取中位数。

**踩过的坑（都已写进 `Docs/ERROR_LOG.md`）**

- 把**两次独立执行**当成 A/B，报出 −17.6%，真实是 −2.2%。此后每个改动都带关闭开关。
- 自己留在背景的 `find` 吃掉 92% CPU，污染所有量测（1.4 s → 31.9 s）。这棵树上 `find` 很慢（45 GB 基础库），
  要用 Glob／grep 指定路径。另外**不要把 `cargo` 程序当成机器在忙** —— 那 18 个 idle 的
  `cargo run ok-game-mcp` 是常驻的 MCP server。
- 凭 SPOT 的次数与总时间推估就报结论（「136 次 `flip_png_v` 是串行的」），其实它们早就在并行的
  `PushCtx::transform` 里。**发现前提错了先把量测补上，再回头讲。** SPOT 的 wall 是**跨执行绪加总又嵌套**
  的，所以不能直接当墙钟做减法（「省掉它能快多少」）。**判断某个数字能不能减的现成检查**（f-sceneload）：
  **把各子项加起来和包住它们的那一段比** —— 落在容器里面（例如三段共 26.0 s 在 `Sync` 的 63.4 s 内）、
  互不嵌套、所在回圈里没有 `ParallelFor`／`par_iter`，才可以减；**加起来超过容器就是跨执行绪加总的**。
- `ls -t Saved/Logs/CardReader/*.log | head -1` 拿到的是**上一次执行的日誌**，两种设定印出一样的数字，
  看起来像开关没生效。改成自己指定 `-abslog=`。
- kill 回圈用 `head -1`，留下 3 个 UnrealEditor（各约 9.5 GB），把 `f-sceneload` 卡在排队、那一轮数字全废。
  **一格 slot 只能有一个 Unreal 程序**；按命令列过滤 kill 并确认 `remaining: 0`。
- 把「精确名字查表」放在**关闭开关的前面**，关掉也享受到新路径 —— 假 A/B。
- **`VAR=$v` 搭配空值表示「不设」：`VAR=` 仍然会把变数设起来**，而开关是 `var_os(...).is_some()`，
  空值也算设了，于是**两边都是关的**。A/B 看起来「优化没用」，而且**那 49 个 dump 的「IDENTICAL」
  什么都没证明** —— 正确性闸门整个空转。是数字自相矛盾（单独跑 537 ms vs A/B 1000 ms）才抓到的。
  **每次 A/B 前先印一行确认开关真的在切。**
- **多行 `perl -0777 -pe 's/…\n…/…/'` 在这棵树上会静静地配不上**：档案是 CRLF，pattern 里的 `\n` 对不上
  `\r\n`，于是**档案没变、`cargo build` 成功、A/B 两边当然一模一样**。11-18 一天就因此产出两个幻觉实验：
  「prefetch helper 数 8／6／4／3 的扫描」其实是把同一个设定量了 12 次（难怪只有噪声没有形状），
  「贴图 memo 放宽」第一次量到的「零效果」也是因为那笔改动从未进档案（改用 `Edit` 重做，立刻看到
  重复 12 → 5）。**多行改动用 `Edit` 或指定行号的 `sed`，不要用 perl 的多行 pattern**；单行 pattern 没问题。
  现成的防线还是同一条：**先证明开关是活的**。这次是加临时的分支计数器才看出改动不在那条路上
  （`branch plain` 41 次、`branch transform` 41 次、`branch memo` **0 次** —— `memosnap::active(TEX)`
  在这些开卡里一直是 false，所以我第一个 single-flight 放的位置是死码）。

- **量测脚本的 `grep` 抓到了另一行**（11-18，这一天第三个「数字是真的、代表的不是那件事」，而且这次是
  我自己的工具）：`grep -oE '[0-9.]+s$' | head -1` 取「第一个以秒结尾的数」，可是 `--sequence` 模式会先印
  `ok-extract: prewarm <库> in 0.46s`，再印真正要的 `ok-card-open-bench: <卡>@0 1.82s`。**于是我整天量的是
  预热自己的耗时，不是开卡**，而预热跑在 below-normal 的自己的池上，两者的改善幅度差了一个量级（预热
  −83%，开卡 −2.3%）。**两笔结论都要重写**（惰性 zip entry 与预热跳过整棵树，第一节改动 6 与第四节）。
  抓到它的不是红字，是**形状可疑**：单卡跑和三卡跑的数字差了 6 倍，而开卡时间不该随卡数变。
  防线：**匹配要钉住自己那行的前缀**（`ok-card-open-bench: .*@[0-9]+ [0-9.]+s`），不要用「最后一个数字」
  这种靠位置的匹配 —— 被测程式多印一行就全盘错，而且不会有任何错误讯息。

**这类坑的共同点（f-sceneload 整理成 F 树 `Docs/ERROR_LOG.md` 的一类，`2026ed16c`，三个实例）**：
失效的是**量测本身**，不是被测的程式，所以**不会有任何红字**——关卡照样 PASS、数字照样印出来。
它找到的辨识法比「要小心」可操作得多：**三个都是形状可疑，不是数值可疑。**
（a）基点在量测中途被别人的合并改掉 → 形状是「**逐位元相同太干净了**」（856 个物件连那 5 个
骨头道具都没差，本来就不合理）；（b）比画面时 shader 还在编译 → 「**退步得太夸张**」（均差 31.8/255，
真的回归不长这样）；（c）我那个 `VAR=$v` → 「**两边一样得太彻底**」。
**数值本身永远看不出量测已经失效**，所以量完要问的是「这个结果的形状对吗」，不是「这个数字合理吗」。
（a）的具体防范：**每组数字记下当时的 commit，不只记日期**，回报前对一次 `git log -1`。

**再广一层**（`8d5a476d6`）：**任何一个结果大到或小到让你想找理由解释它，先怀疑量测——想解释一个漂亮
或难看的结果，这个冲动本身就是讯号。** 这条比「怀疑量测」更广，因为它也抓得到**数字是真的、但不是你
以为它代表的那件事**：f-sceneload 报过「16 542 → 8 023 ms（−51%）」并替它找到合理解释（父行程不必自己
付转卡暖机），所以停止怀疑；后来量峰值记忆体才发现那是 `workers=8`（约需 16 GB），使用者实际拿到的
是预设 2 的 −28%／−34%。**这里的数字没错，错的是它代表谁的体验。**
所以每个回报出去的数字都要连同「在什么设定下量的」一起写——这份文件里每个数字都标了条件，原因就是这个。

  **读程式码找到的候选（11-18，整合 #16 后；还没量，所以还不是结论）：那 3.2 GiB 大半可能是
  「为了读名字而复制位元组」。** 这个 codebase 里 `zip.by_index(i)` 会走到 `gamefs.rs` 约 1390 行，

  走遍每个 entry 只为了看名字：
  - `mods.rs` `zipmod_one_unity3d_uncached`：`for i in 0..zip.len()` 全部 `by_index(i)`，只取 `f.name()`

  PNG entry —— 全部复制一遍只为找到一个 `manifest.xml`，正好对上量到的

  **第 0 步，先确定是谁在扫（一条命令，不要猜）。** 同一张卡量两次 `copied out of the sources`：

  惰性，差不多就回到第 1 步那条「哪些项目用不到」的路。**这一步只加计数、不改行为**，所以可以在任何时候
  跑（它是计数，不受机器负载影响）。

  **第 1 步，证明不变 —— 不是用路径名字说服自己，是用输出位元组。** 惰性那个修法**不该**改变任何输出，
  所以闸门是「全部相同」；若走的是「跳过某类项目」那条路，则要先让那条扫描跳过要砍的那类项目（带关闭

  2. **串行链里「比值 ≈ 1」的那几段**（它们才是自己的工作）：`head_detail` 72＋`clothes` 74（含 `gpu bake` 31）＋`subclothes` 44＋`face overlays+emit` 42＋`compose_face_texture` 35 ＝ **267 ms**。其余各段比值都 ≥1.5（在等别人，或自己已经并行），重排它们量过四次都是零（第二节）。
  3. **理想值**：这 267 ms 全部完美并行到 8 条执行绪 → 267/8 ≈ 33 ms，**省 234 ms = −27%**，冷开 869 → 635 ms。这是**上限**，而且是「每一段都拆成三段式、每一段都拿到满分」之后的上限。
  4. **实际能拿到的大约是上限的一半**：已经做完的 `head_detail` 是这类里最干净的一个（14 个独立 mesh、没有 GPU、没有顺序），它拿到 **−3.4%，而它自己的上限是 −6.8%** —— 成本不均（最贵的那个 mesh 就是 Amdahl 的分母）。照这个比例，整条链全做完约 **−13%（869 → 760 ms）**，要**五到六次**和改动 10 同等规模的重构，而其中 `clothes` 那段还卡着 GPU 装置不是 `Send`（只能合批，不能搬）。
  5. **使用者的目标机更不划算**：低核机上并行最多只有 2 倍，同一笔 267 ms 的理想值是省 133 ms／1220 ms = **−11% 的上限**，实际约 −5%。（这和改动 9 的 BC7 刚好相反：BC7 是「同样的工作少花 CPU」，核心越少越赚；**拆段是「把工作摊到更多核心」，核心少就赚不到**。两类改动要分开看。）

  **结论：冷开已经接近这个架构的下限，继续拆段的投报率很低。** 整条链全做完的上限是 −27%、实际约 −13%，而那是五六次动在开卡最要紧那段程式码上的重构，每次都要 84～252 个 dump 的逐位元组闸门。**这条线到此为止**；真要再往下，剩下的两个方向都不在「拆段」里：

  - **总量变少**（使用者还没决定的「把底图缩小」，本节上面那条）—— 它动的是 `lists` 窗口与贴图还原的真工作，也就是上面第 1 项那块算成地板的 286 ms，天花板比拆段高得多。
  - **同样的工作少花 CPU**（改动 9 那一类：换更快的解码／少做一次复制）—— 低核机上直接变墙钟，而且不必动开卡的结构。

## 五、执行绪预算

这一轮动过执行绪的配置，三件事写在这里省掉下一个人误用。

### 改了什么

| 提交 | 改动 |
|---|---|
| `1a3a55dc2` | 全域 rayon 池从写死 `num_threads(MAX_THREADS)` 改成 `cpu_threads()`；`cpu_threads()` 除了 `OK_THREADS` 也读 `RAYON_NUM_THREADS` |

两个背景事实：`RAYON_NUM_THREADS` **从来没有生效过**（明确给了 thread count 的 rayon 池不会再读环境变数，
而写死的值刚好也是 8，所以没人发现）；而 `limit_threads()` 原本只有 `main.rs`（`ok-extract`）与 `ffi.rs`
（UE）叫，17 支工具一支都没叫。细节与防范在 [ERROR_LOG.md](ERROR_LOG.md) 的 2026-11-17 各条。

### 一、转卡／开卡这条路加宽执行绪几乎买不到东西

它是单执行绪与 IO 为主，加上 GPU 烘焙。f-sceneload 在同一张卡上交错三轮取中位数（`card-outfit`）：

| 一个行程拿到的执行绪 | wall 中位数 | CPU 中位数 |
|---|---:|---:|
| 8（不给 `[threads]`） | 5.01 s | 8.92 s |
| 4 | 5.15 s | 8.27 s |
| 2 | 5.30 s | 7.92 s |

8 → 2 条：wall 只多约 6%、CPU 省约 11%，峰值记忆体不随它变（2.34–2.38 GB）。

所以 **`cpu_threads()` 能被环境变数调高，价值完全落在批次工具那边**（`ok-lowpoly`、`ok-crowd-pack` 一次跑
几十张卡的离线工作），**不能拿转卡／开卡的数字替它背书**。这条路要快得靠「少做事」——共用树的暖机、少开
几次 session——不是靠多给执行绪；执行绪数在这里只是「守机器规矩的代价」那一面。

### 二、「批次工具慢 4 倍」是机制推估，没有量过

把工具从 32 条限回 8 条之后，我警告别组「可能接近 4 倍慢」。**那是从 32 ÷ 8 推的上限，不是量到的，
而且我自己手上的数据就反驳它**：同一个 bench 没有 `limit_threads()` 时拿满 32 条是 1172 ms、补上之后
8 条是 1298 ms，**只差约 10%**，而那段里本来就有一块宽 rayon 的逐 texel 工作（颜色遮罩烘焙）。这类工作离
线性扩展很远。

`ok-lowpoly` 本身**量不了**：它要 PNG 里有 portable snapshot（`okPv`），手上的 `CrowdAPNG/C001.png` 报
"PNG has no portable snapshot"，所以没有能喂给它的输入。要确定得用 C 组自己的卡与 `--budget` 实际跑一次。

**所以不要在任何地方留下「4 倍」这个数字当事实。** 正确的说法是：机制上确实变慢（32 → 8 条），幅度未量，
同类工作的唯一实测是约 10%。

### 三、这一节的数字本身就是「别用单趟去量」的例子

上面那张 8／4／2 的表，第一次只量了单趟，得到的是「8 条比 4 条快 **0.8 s**」，而且 4／2／1 三栏不单调
（4 条比 1 条还慢）——非单调就是噪声在主导的讯号。交错三轮取中位数之后，真正的差是 **0.29 s**，一半是噪声。

而且**跨时段的绝对值完全不能比**：单趟那次的绝对值是 6.5–7.4 s、交错那次是 5.0 s，差别不是改动造成的，
是前一次量的时候机器上有别组的全跑在吃资源。

被推翻的 0.8 s 刻意留在这里，不是只留正确答案——下一个人要知道的是**别再用单趟去量这件事**。

## 八、原作卡只读它需要的 mod（2026-11-22，C 树）

**决定（2026-11-24，使用者）：这些第三方 mod 模型要算共用资源**——理由是它们在角色之间本来就是共用的

落地时分成两件事，**第一件已经做了，第二件卡住了**：

**一、打包带上那些模型（速度目标，已做）。** 原作卡的开卡**不是**严格开卡（`okstrict` 只管 OK 卡），所以
只要打包清单带上那些模型，打包版开原作卡就直接读庫、不必现转——这正是先前量到的 load3d 6.9 → **2.66 s**、
Rust 开卡 5.1 → **1.65 s**（那次只换了 `OK_BASE_LIBRARY`，**没有改任何规则**）。所以
`original_data_manifest.json` 的 `base-models` 群组改成整个 `base_v1/models`（4544 个档），私有打包就会带上它们；
**分类规则不动**，既有 OK 卡与开卡行为完全不变。
使用者的验收标准：重新打包后，**打包版开原作卡三张基准要接近 1.35／0.59／0.62 s**（那是 bench 只量 Rust 开卡
那段的数字，所以打包版也要量同一段来比：`OK_PROFILE` 现在会进游戏日誌）。

**二、让 OK 卡不再各封一份（卡片大小，已落地）。** 把「共用」拆成**两个判断**，各读各自的产生档
（`ok-extract <游戏> --oklib shared-ignore <庫>` 两份都产生）：

| 判断 | 读哪个档 | 问的是什么 | 整棵树那行 `mods/` |
|---|---|---|---|
| `okstrict::library_zip`／`library_entry` | `shared_mods.txt`（全部行） | 哪些**封存档**庫可以服务 → 封卡就不必录它们的 bundle | **算进去**（整棵树都算共用） |
| `okstrict::library_model` | `models/.gitignore` | 哪些模型**录下来的答案**可以跨卡重用 | **刻意忽略** |
| `okstrict::shared_mods_visible` | `shared_mods.txt` 的**具名行** | 原作卡的窄 mods 视图要列哪些 zipmod | **刻意忽略** |

第二列忽略整棵树那行，是因为「答案」的有效性是按卡的（服装状态、窄 mods 视图、当时在视野里的东西都不在
key 里），拿庫为别张卡录的答案回答这张卡会**静静地给出偏窄的结果**。第三列忽略它，是因为那行讲的是「庫可以
服务这些封存档」，不是「每个 zipmod 都该进某张卡的视图」——照字面解会把约 7300 个 zipmod 全放回视图，
把第八节的 8.9 s → 1.9 s 连同全树模式捡错东西的那些 bug 一起请回来。

**闸门（干净机器，逐位元）**：OK 卡六张的全部服装 **42/42 相同**、原作卡三张基准 **21/21 相同**。
**封卡实测**（同一张 Tohru 两种规则各封一次）：**70,978,567 → 64,591,890 bytes（−6.39 MB，−9.0%）**，
两张卡都开得起来、没有任何 gap 或未回答的问题，而且 7 套服装开出来的 session 逐位元相同。

**这条的代价**：翻规则之后封的卡**依赖基础庫有那些封存档**（它们现在算共用资源），所以在基础庫没有它们的
机器上开不起来——打包清单已经带上全部模型（上面第一件），所以打包版没问题；要给别人的机器就要确认那边的
基础庫是从同一批 mod 转出来的。要回到旧规则：删掉 `Tools/base_library_shared_mods.txt` 里那行 `mods/`，
重跑 `shared-ignore`，既有的卡不受影响（它们自带那份照旧）。

**一笔自己量过又推翻的结论（照规矩留着）**：我先前写过「拆成两个判断也救不了，翻规则不可能让卡变小」。
那是从 `OK_OWN_ANSWERS=*` 的失败推过去的——但那个实验把**封存档与模型答案两边一起**关掉了，所以它只证明了
「两边都关会让卡开不起来」（严格开卡是重播，没有 bundle 可以重算），**没有**证明「封存档算共用也不行」。
真正的分界其实更早的二分就量到了：A 组态（封存档算共用、模型答案照旧）当时 C049 两片大腿都在。
**教训**：一个实验同时关掉两个开关，就只能回答「两个都关会怎样」，别拿它去否定其中一个。

同一轮修掉一个两边矛盾的判断：`shared-ignore` 原本把「没有记录来源」的模型算非共用，而同一个命令里
`split-local` 的注解说这种模型可能是别棵 checkout 的共用模型、应该留下。现在一律留在共用侧（39 个，
共用 614 → 653 个／6.51 GB），三张卡 21 套 dump 逐位元相同。

**两个量测陷阱**（这次就是踩在这上面才看起来像回归）：

1. **`load3d` 不是 `ok-card-open-bench` 量的那个数**。load3d＝Rust 开卡＋UE 侧建资源（这次是 5.1＋1.0），
   而第一节的基准只有 Rust 开卡那段。拿 6.9 s 去对 4.4 s 等于把两种东西相减。
2. **打包版的基础庫跟本机的不是同一份**。同一个执行档、同一张卡，只换庫就是 6.9 s 对 2.7 s。
   报「某个 commit 让开卡变慢」之前，先确认两边的庫一样；`base_v1/models` 的目录数与容量一看就知道。

### 两张文字表变成基础庫里的一个 DB（2026-11-24）

所以禁止的是**每张卡**的快取（开卡答案、衍生贴图、`OK_LIBRARY_CACHE`），而共用基础庫自己带的索引本来就该做成 DB。
`mods_guids.txt` ＋ `mods_overrides.txt` 因此换成 **`<庫>/mods_index.db`**（SQLite，3.9 MB，schema 1，产生时先写
`.db.new` 再改名；旧的两个文字档会被删掉）：

| 表 | 列数 | 内容 |
|---|---:|---|
| `archive` | 7296 | 安装目录每个 zipmod 的相对路径，**`id` 就是走访顺序**（所以查询一律 `ORDER BY a.id`，候选的先后不另外存） |
| `guid` | 7296 | `guid`（索引）／`version`／`archive` |
| `override` | 23752 | `bundle`（索引）／`archive` |
| `meta` | 6 | schema、列数、建的时间、**`mods_dir`**（是哪一棵树） |

开卡只做**点查询**，整表只在一个地方读：读卡器自己的 GUID 索引。UE 不自己开 SQLite——FFI `ok_library_mod_guids`
→ `FOkSession::LibraryModGuids` 把 `guid<TAB>version<TAB>相对路径` 一次交给 `FKKModIndex::LoadGuidRows`，
格式只有 Rust 一个主人（`FKKModIndex::LoadLibraryGuids` 不再存在）。

**量出来的两个陷阱**（都在「这棵树是不是索引说的那棵」上）：

- `serves()` 本来是「视野里有没有任一 archive 被索引认得」，而视野＝**列**整棵树的档名，且它的 memo 键是
  fallback generation，每张卡都会变。于是连 OK 卡（根本没东西要问索引）每开一张都白列 7296 个档名。
  现在先比 `meta.mods_dir`（一个字串，不碰档案系统），只有路径不合（搬过的安装、测试的临时树）才退回列树。
- `guid_archive`／`override_archive` 要按「当前视野」挑候选，同样会列树。现在 `visible()` 在
  **没有窄视图**（`gamefs::narrow_mods_active()` 为假）且 DB 就是这棵树时回 `None`＝全部可见，完全不列。

**闸门**（同一个庫、同一批卡，`--fresh-dump` 逐位元，对照组是改动前的二进位）：原作卡三张 **21/21 相同**、
OK 卡六张 **42/42 相同**、开卡读的 manifest **0**、未答覆的只有本机没装的那几个 GUID。
`cargo test --lib`：548 passed，1 failed（`appearance::properties::plugins::...known_integer_and_string_fields...`，
F 组 65551a150 带进来的既有失败，和这笔无关）。两个 UE 目标（`OpenKoikatsu`、`OpenKoikatsuEditor` Development）都连结成功。

**读卡器实测**（伊莉雅，同一张卡，冷开）：`OK reader mod index: 7273 GUID ... in 45 ms`（文字档版是 16～18 ms：
整表查询＋FFI 一趟比 parse 文字稍贵，但对原本的 2.8 s 来说两者都是零头），开卡 `extract_card_outfit TOTAL`
1525.7 ms，落在文字档版那四轮（1487～1787 ms）的区间里。

**量测注意：incremental release build 本身就值约 4%。** 六张 OK 卡交错三轮（中位数、总和）：
改动前的二进位 5.30 s、现在的 incremental 建置 5.70 s（+7.6%）、**同一份程式码用 `CARGO_INCREMENTAL=0` 全新建置
5.49 s（+3.6%，当轮旧二进位自己的散布就有 5%）**。`Cargo.toml` 的 `[profile.release] incremental = true` 是全专案共用的，
`build-release.cmd`（Unreal 连结的那份）也吃它，所以 A／B 比时间一定要两边同样的建置方式，不然会把 codegen 的漂移
当成改动的代价。

### unanswered 的分类：什么该问 mods 索引、什么不该（2026-11-24）

打包版 `Release1124e` 的实测把 `OKMODS unanswered` 的噪音暴露出来：伊莉雅那张卡印了八行，其中只有一行是真缺件。
分三类，判准和证据如下（证据都是直接读 `D:\KoikatuSunshinezz\mods` 里那几个 archive 的 `manifest.xml`）：

| 这个 id 是什么 | 例子 | 怎么判 | 现在怎么报 |
|---|---|---|---|
| 安装目录**自己要迁移掉**的旧 id | `kks.co_bra_00`、`kks.co_shoes_35` | 索引新增的 `migration` 表（`guidOld`／`migrationType`，219 列）：`kks.backport.clothes.zipmod` 的 `MigrateAll`、`[KKS]KK_Backport_Compatibilty.zipmod` 的 `StripAll` | `OKMODS migrated guid: ...`，不算缺件 |
| UncensorSelector 的**部件 id**，不是 zipmod GUID | `SAC.clit`／`SAC.clit2`／`SAC.innie`／`SAC.innie2`／`SAC.roastie2` | 它们只出现在 UncensorSelector 自己的 manifest 里（`<body><guid>`、`<migration><guidUncensor>`），不是任何 archive 的 `<guid>`；用 `uncensor_guid_known`（庫的 `uncensor_v1`，25 个包，memo 过）问 | `OKMODS uncensor part: ...`，不算缺件 |
| **真的没装** | `kiyoubi. illya` | 索引里没有，整棵树的 manifest 里也搜不到 | `OKMODS unanswered guid: ...`（真缺件） |

伊莉雅那张卡于是从 8 行变成 **1 行**（`kiyoubi. illya`），而且逐位元闸门不动（原作卡 21/21、OK 卡 42/42）——
分类只改怎么讲，不改怎么解析。`migration` 表走同一次建庫的走访，`--oklib mods-index` 一起产生，schema 升到 2。

**「GUID 被截断」那件不是 bug，是作者自己写的。** `[kiyoubi] BIKKE_v0_1.zipmod` 的 manifest 原文就是
`<guid>youbi. BIKKE</guid>`（`<author>kiyoubi</author>` 另外一行），所以索引里的 `youbi. bikke` 是忠实的。
Sideloader 的 GUID 是作者自订字串，7273 个键里有 **1704 个**含空白或 `[a-z0-9._+-]` 以外的字元
（`0083_apex legend`、`3d scans`、`6607asdg eye`…），所以「看起来怪」不能当成解析坏了的判准。
`kiyoubi. illya` 同理：它是伊莉雅那张卡自己写的 id，整棵树里没有任何 archive 提到 illya，就是没装。

### 讀卡器那兩秒：已經排除掉的（2026-11-24，還沒定案）

Megumin 同一張卡、同一套 outfit 0、同一個庫：bench 1.17～1.30 s，讀卡器 3.5～4.1 s（閒置後再開也是 3.0 s）。
差的兩秒集中在 `clothes options`（每個部件 39～184 ms，bench 是 **0.2 ms**）與 `clothes renderer map`（同樣量級）。
這一輪把候選一個個排掉，**剩下的唯一活口是那兩段裡面沒有被 spot 包住的 bundle 物件讀取**：

| 候選 | 怎麼測 | 結果 |
|---|---|---|
| 卡不同／服裝不同 | 那張卡七套服裝都 bench 過 | outfit 0 = 1.31 s，其餘 0.21～0.25 s；沒有一套接近 3 s |
| 啟動爭用 | 閒置後從 UI 再開同一張兩次 | 3.02／2.99 s，和啟動時那次一樣 |
| 背景的 clothing warm 搶資源 | `OK_NO_CLOTHING_WARM=1` | 3.66 s vs 3.78 s，沒差 |
| 機器的檔案快取被 UE 擠掉 | 讀卡器開著閒置時，另一個 bench 行程開同一張卡 | bench **1.48 s**，`view: zip_list_sig` 3.2 ms、`open_zip` 7.8 ms——同一分鐘內，同一棵樹，行程外面很快 |
| 窄視圖沒生效（整棵樹） | bench 加 `OK_WHOLE_MODS_TREE=1` | 1.17 → 1.69 s（`open_zip` x22037），只值 0.5 s，解釋不了兩秒 |
| 執行緒不夠 | bench 8/4/2/1 執行緒 | 1.30／1.41／1.67／2.45 s，只解釋一部分 |
| entry prefetch 沒跑或在等 | 兩邊的 `PROFILE prefetch`、`SPOT prefetch hit (wait)` | 完全一樣（14 groups、8 helpers、0 miss；等待 3.4 vs 4.8 ms） |
| 拿 bundle bytes 或 parse 變慢 | `SPOT accessory_bundle_bytes`、`SPOT parse_bundle_uncached` | 0.0 ms x8；31 ms x101（件數一樣） |
| mesh 解碼搬位置了 | 兩邊的 `PROFILE segments` | 都有，讀卡器**還更少**（1059 vs 1541 ms，跨執行緒加總） |

也就是說：**件數一樣、CPU 更少、時間多兩秒**，而且外面的行程同時測是快的。下一步是在
`unity::clothes_option_groups` 與 `unity::clothes_renderer_map` 裡面加 spot（現在那兩段裡只有進出的 tick，
中間沒有量測），特別要分出「讀 bundle 物件時的 page fault」——那兩段吃的是 `SourceBytes`，mmap 的頁在 UE 行程裡
可能沒有住在記憶體裡，而 page fault 既不算 CPU、也不會出現在任何 spot 上，正好符合上面這組症狀。
