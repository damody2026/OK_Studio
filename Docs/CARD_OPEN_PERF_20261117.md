# 开卡性能优化（2026-11-17，E 树）

**使用者会感受到什么**（只看这两句就够）：
**打包版（只有 OK 卡）**——开第一张卡快约 0.4 s（1.52 → 1.27 s，−16.8%），之后每张只快一点
（四张合计 −2~5%），因为 OK 卡不读 mods 树，拿到的只有颜色遮罩那一项；读卡器启动后多花几百毫秒
在背景预热，换来第一张卡少付约 150 ms。**自己开原作卡（有遊戏目录与 mods）**——第一张差不多
（5.0 → 4.4 s），**但第二张之后快三到四成**（第二张 4.24 → 2.32 s、第三张 4.81 → 3.37 s），
也就是在读卡器里一张张翻卡的实际体验；另外把整个场景转成 OK 卡快约一成（21 角色 74 → 67 s）。

目标：让「开卡」（读卡器打开原作 KKS 卡与 OK 卡到可显示）实际变快。**前提：开卡的磁碟快取永久关闭**
（`70d8a21c7`，2026-10-28，多程序正确性；使用者 2026-11-17 再次确认「永远不要开开卡快取，想办法优化冷读取」），
所以**唯一的基准是「全新程序、无快取」的冷开**。

这份是独立的最终版，接手不必读任何对话。按时间顺序的过程记录（含被后续推翻的中间结论、各阶段的原始
分解数字）在 `Saved/Reports/card-open-perf-20261117/README.md`，**那是本机产物、不进版控**，可能被清掉；
需要长期保存的结论都在这份文件与 [ERROR_LOG.md](ERROR_LOG.md) 的 2026-11-17 各条里。

## 二、做了之后回退或放弃的（和收益一样重要，省掉重走一遍）

| 项目 | 量到的事实 | 处置 |
|---|---|---|
| ④`read_strip_all_guids` 併集 | 走树与併集都已免费，成本全在 7300 次 `zip_memo`，其中 97% 是 `fallback_serving_id`。**但那 430 ms 是冷的 Windows 目录元数据**：短路掉它之后这一阶段只剩 18 ms，而且开关开与关都是 18 ms。一次开卡要读几百 MB bundle，会把目录元数据挤出快取，所以下一张卡的全树 stat 又回磁碟（暖 18 ms／被挤掉 250–400 ms／第一张 1.3–1.6 s）。三种做法（serving memo 改吃 `fallback_identity` token、`resolve_mod_archive` 线性扫描换查表、whole-tree pass 并行）交错 A/B 都拿不到 | 全部回退 |
| `fallback_serving_id` 能不能省掉 | 不能。`open_zip` 的 replay 分支对「library 记录了但本机没有模型」的档案本来就 `fallback_source` 去 stat，而 `real_zip_matches_recorded` 不符时会 `open_real` 直接读真档 —— manifest 真的可能来自真档，键不含 serving id 就会重现 2026-11-12 花火那个 bug | 保留现状 |
| ②`slot colour` 编解码融合 | math 占 88%（939 ms），PNG 往返只占 12%（decode 91 ms／encode 43 ms），拿不到原估的 80–120 ms | 放弃 |
| ②「以为烘焙把遮罩升采样到 4096²」 | **错的前提，而且是我自己写的注解造成的**。4096 是 mod／原作 Texture2D **自己的尺寸**，程式码没有 4096 常数也没有任何 resize；遮罩一直是逐输出 texel 按需读，没有放大后的缓冲区。那 939 ms 是「产生一张 4096² albedo」本身的逐 texel 成本 | 这条路径无事可改；结论已写进 `clothes_texture.rs` 的注解 |
| `GridSampler` 的 point 快路径 | 以为同尺寸时权重为 0 可以少读三个 texel；`OK_GRID_DIAG` 印出来才知道真实情况是 64²／512² 升采样到 4096²，权重本来就不是 0 | 整个回退，只留诊断 |
| ③`emit` 并行 | 整个 emit 阶段占三张卡总时间 2.2%（`memo_put` 19 ms＋`ctx.emit` 54 ms）。`memo_put` 搬不走（`view_memo` 是 thread-local）；`ctx.emit` 的每项工作是 `emit_part` 往 `session_parts` 后面 append，后面还有四处 `last_mut()` 改刚 append 的那一项 —— **顺序就是这个资料结构本身** | 不做，只留三个子计时 |
| `BUNDLE_CACHE`（`parse_bundle_cached` 的 thread_local）改程序共用 | `ParsedBundle` 有 18 个 `RefCell` 栏位且 `external_files` 装 `Rc<ExternalFile>` → `!Send + !Sync`，**型别上就放不进跨执行绪的 static**；还骑着「OK 卡资源包只记录真的跑过的查询」这条不变式（F 组 11-16 alice 那个 bug 的同一类）；`TEXTURE_CACHE_BYTES` 已经是每 bundle 192 MiB、每执行绪各一份。`native_workers_broadcast` 也救不了，因为 `base: head textures` 是在开卡那条执行绪上同步跑的 | 不做 |
| 拿掉 `library_zip_memo` 的 strict 闸门（让 OK 卡也共用按 archive 的新键）<br>`d352dcb90`，整合 #15 后做的 | gap guard（`0dbce369f`）进来之后这道闸门的理由就过期了，所以照计划拿掉并重验 —— **零收益**：同行程 5 张 OK 卡，共用 1498 次 `open_zip`、不共用 1503 次（噪声内），35 个 dump 两边逐位元相同。**开关是活的**（同一执行档两张原作卡 38094 对 52645 次），所以这个零是真的。原因是设计使然：**OK 卡自带资源包**，读的档案几乎都来自自己的包，走 `own` 分支本来就保留 generation；只有「library 记录的档案」能共用，而 OK 卡几乎不读那些 | **放回去**，只留注解写明不要再试（在两次严格开卡之间共用值正是 pack 身分要防的：花火 11-12、alice 11-16，没有收益去换这风险） |

## 三、量测方法与陷阱

**方法（这台机器上唯一可信的做法）**

1. **只量冷开**：全新程序、无快取。磁碟快取永久关闭，所以没有「暖」这个基准。
2. **同一个执行档＋环境变数开关＋交错＋同时段＋取中位数**。不同次执行之间的差异不算 A/B。
3. **正确性用 `--fresh-dump` 逐位元组比对** session bytes（不是整档雜湊，见 ERROR_LOG I-014）：
   OK 卡 28 个 dump（C001／C006／C049／klara／C050／megumin，含 override 与眼睛贴图）＋原作卡 21 个。
4. 一切建置与量测**最多 8 执行绪**（`cargo -j 8`、`-MaxParallelActions=8`、`RAYON_NUM_THREADS=8`）。
5. 会改变输出位元组的改动（例如缩小底图）**不适用**第 3 条，要改成目视＋平均 RGB 绝对差＋贴图记忆体。

**踩过的坑（都已写进 `Docs/ERROR_LOG.md`）**

- 把**两次独立执行**当成 A/B，报出 −17.6%，真实是 −2.2%。此后每个改动都带关闭开关。
- 自己留在背景的 `find` 吃掉 92% CPU，污染所有量测（1.4 s → 31.9 s）。这棵树上 `find` 很慢（45 GB 基础库），
  要用 Glob／grep 指定路径。另外**不要把 `cargo` 程序当成机器在忙** —— 那 18 个 idle 的
  `cargo run ok-game-mcp` 是常驻的 MCP server。
- 凭 SPOT 的次数与总时间推估就报结论（「136 次 `flip_png_v` 是串行的」），其实它们早就在并行的
  `PushCtx::transform` 里。**发现前提错了先把量测补上，再回头讲。** SPOT 的 wall 是**跨执行绪加总又嵌套**
  的，所以不能直接当墙钟做减法（「省掉它能快多少」）。**判断某个数字能不能减的现成检查**（f-sceneload）：
  **把各子项加起来和包住它们的那一段比** —— 落在容器里面（例如三段共 26.0 s 在 `Sync` 的 63.4 s 内）、
  互不嵌套、所在回圈里没有 `ParallelFor`／`par_iter`，才可以减；**加起来超过容器就是跨执行绪加总的**。
- `ls -t Saved/Logs/CardReader/*.log | head -1` 拿到的是**上一次执行的日誌**，两种设定印出一样的数字，
  看起来像开关没生效。改成自己指定 `-abslog=`。
- kill 回圈用 `head -1`，留下 3 个 UnrealEditor（各约 9.5 GB），把 `f-sceneload` 卡在排队、那一轮数字全废。
  **一格 slot 只能有一个 Unreal 程序**；按命令列过滤 kill 并确认 `remaining: 0`。
- 把「精确名字查表」放在**关闭开关的前面**，关掉也享受到新路径 —— 假 A/B。
- **`VAR=$v` 搭配空值表示「不设」：`VAR=` 仍然会把变数设起来**，而开关是 `var_os(...).is_some()`，
  空值也算设了，于是**两边都是关的**。A/B 看起来「优化没用」，而且**那 49 个 dump 的「IDENTICAL」
  什么都没证明** —— 正确性闸门整个空转。是数字自相矛盾（单独跑 537 ms vs A/B 1000 ms）才抓到的。
  **每次 A/B 前先印一行确认开关真的在切。**

**这类坑的共同点（f-sceneload 整理成 F 树 `Docs/ERROR_LOG.md` 的一类，`2026ed16c`，三个实例）**：
失效的是**量测本身**，不是被测的程式，所以**不会有任何红字**——关卡照样 PASS、数字照样印出来。
它找到的辨识法比「要小心」可操作得多：**三个都是形状可疑，不是数值可疑。**
（a）基点在量测中途被别人的合并改掉 → 形状是「**逐位元相同太干净了**」（856 个物件连那 5 个
骨头道具都没差，本来就不合理）；（b）比画面时 shader 还在编译 → 「**退步得太夸张**」（均差 31.8/255，
真的回归不长这样）；（c）我那个 `VAR=$v` → 「**两边一样得太彻底**」。
**数值本身永远看不出量测已经失效**，所以量完要问的是「这个结果的形状对吗」，不是「这个数字合理吗」。
（a）的具体防范：**每组数字记下当时的 commit，不只记日期**，回报前对一次 `git log -1`。

**再广一层**（`8d5a476d6`）：**任何一个结果大到或小到让你想找理由解释它，先怀疑量测——想解释一个漂亮
或难看的结果，这个冲动本身就是讯号。** 这条比「怀疑量测」更广，因为它也抓得到**数字是真的、但不是你
以为它代表的那件事**：f-sceneload 报过「16 542 → 8 023 ms（−51%）」并替它找到合理解释（父行程不必自己
付转卡暖机），所以停止怀疑；后来量峰值记忆体才发现那是 `workers=8`（约需 16 GB），使用者实际拿到的
是预设 2 的 −28%／−34%。**这里的数字没错，错的是它代表谁的体验。**
所以每个回报出去的数字都要连同「在什么设定下量的」一起写——这份文件里每个数字都标了条件，原因就是这个。

**留下的诊断**（都是环境变数开关，关掉时零成本）

| 变数 | 作用 |
|---|---|
| `OK_PROFILE=1` | 阶段计时。本轮新增 `batch: slot colour`／`slot finish`／`keys+memo`／`transform`／`emit`，`emit/memo_put`、`emit/regroup`、`emit/ctx.emit`，`base: head textures`、`base: head shape keys+md`、`base: body dynamics+colliders`，`mask bake: decode`／`math`／`encode` |
| `OK_GRID_DIAG=1` | 一次烘焙的贴图与遮罩尺寸、filter |
| `OK_TILE_DIAG=1` | 同值 texel 比例、`has_pat`，以及查表／逐 texel 两条路径各处理多少 texel |

**关闭开关**（做 A/B 用，也是出问题时的退路）：`OK_COARSE_ZIP_MEMO=1`、`OK_NO_ROOT_PROBE=1`、
`OK_NO_TREE_WALK_MEMO=1`、`OK_NO_CHAINED_BODY=1`、`OK_NO_BASE_BUNDLE_PREWARM=1`、`OK_NO_MASK_RUNS=1`、
`OK_NO_MATERIAL_PRELOAD=1`（UE 侧）。

## 四、还没做的

- **把底图缩小换速度与 VRAM**：等使用者决定。一张 4096² RGBA8 解码后 64 MiB，一张卡的重烘焙可以有 4 张
  （256 MiB），在 8 GB VRAM 的目标机上可疑；但**底图的细节不是遮罩给的**，缩的是底图自己那 4096² 的花纹、
  缝线、字样，不是只掉插值。会改变输出位元组，所以验证标准要换成目视（配件上色／头发上色／眼睛贴图／
  有 override 贴图的卡，正面＋近拍）＋改前后平均 RGB 绝对差＋贴图总量。
- **第一张卡 `base: head textures` 还有约 190–200 ms** 没搬走，原因见第二节 `BUNDLE_CACHE` 那一列
  （要搬得先重构 `ParsedBundle` 的内部可变性模型，代价远大于收益）。
- **转卡的 view 身分已改由树的内容决定**（`baf5cec10`）。21 角色场景（`koikatu_cs0001521`）同行程依序转，
  同一执行档用 `OK_CONVERT_VIEW_COUNTER=1` 交错 3 轮：**74 s → 67 s（−9.5%）**，区间不重叠
  （关 73／76／74，开 66／67／68），每张约省 0.33 s；5 张卡那组是 15 → 12 s。
  f-sceneload 指出 5 张卡那组**低估**了它：worker 从队列拿卡，5 张卡时每人只转 2–3 张，吃得到暖机共用的
  只有后 1–2 张；21 张卡在它定的预设 worker=2 时每人依序转约 10 张，19/21 张都吃得到。
  21 张卡的 digest 与 parts 在开关两边**全部相同**（比两张卡的次序关卡更强的正确性证据）。要再往下拿，
  还有两处挡着，都查过了：
  1. `entries.rs` 的 `pack_memo` 键里有 `gamefs::fallback_generation()`，而它每次 `set_fallback` 都递增，
     所以光改 view 身分不会让它跨卡命中。要共用得先想清楚「同一棵树、不同卡包」在那层安不安全。
  2. `unity/references.rs` 的 `inventory_signature` 在严格开卡时直接回传 `"ok card:<identity>"` 当来源
     epoch，注解写着「the card's own pack has its identity」—— 它**预设身分是每张卡一个**。身分改成按树
     之后这个前提就不再成立；目前靠次序关卡与 5 张场景卡的实测确认没有问题，但再动这一带的人要先看它。

  **正确性证据分两半，两半都有了**：同行程依序那半是我验的（21 张卡的 digest 与 parts 在开关两边全相同）；
  **跨行程那半由 f-sceneload 在含这笔的建置上补齐**（`339a526b4`）——`ImportCardWorkers 0`（一个行程连转
  21 张，走这笔的 memo 重用）对预设（4 个行程各转约 5 张，每个自己从树导身分），21 角色场景 856 个物件
  （`map_parts` 331）只差 5 个挂在角色骨头上的道具，id `[3, 276, 280, 292, 577]`；5 角色场景逐位元相同。
  那 5 个**在同一设定的两趟之间也会差**（道具座标随动画相位走），而且**换掉 view 身分的实作之后差的还是
  同一组 id** ——若是这笔造成的，差的该是别的物件或数量会变。两个独立证据都指向它与这笔无关。
  **整合后在 `e7b34e6f2` 上还有更直接的一笔**（f-sceneload，`6824c7e30`）：转卡次序关卡 **PASS**，8 笔
  （正序 4、反序 4）全部一致，而**这一关的基准本来就是一张卡一个行程**，正反序是同一行程依序转，比的是
  开起来的 session 位元组——所以 PASS 就等于「**子行程转卡 == 行程内转卡，逐位元组相同**」，不必另外
  设计实验。**它能一次覆盖两件事**（我的 view 身分在同行程多卡之间不串、子行程转卡与行程内转卡逐位元组
  相同），是因为它的基准恰好是一张卡一个行程，不是谁设计出来的。在这之前跨行程只有 UE 侧的物件傾印验过，

  同一基点上开卡退路那一关也 PASS（`failed_remake_leaves_the_card_openable`，17.57 s）——它现在的用处
  不是把关而是**现况证据**：`e7b34e6f2` 上「OK 卡失败另存后仍可开」有一笔带条件的 PASS 可以对照。
- **这项的收益和「子行程并行转卡」互相抵销**，定 worker 数之前要知道（实测 5 张场景卡）：

  | | wall | CPU 合计 |
  |---|---:|---:|
  | `OK_CARDS_WORKERS=5`（被 clamp 成 4），计数器 | 7.6 s | 17.8 s |
  | 同上，按树 | 7.2 s | 18.3 s |
  | `OK_CARDS_WORKERS=2`，计数器 | 8.6 s | 13.1 s |
  | `OK_CARDS_WORKERS=2`，**按树** | **7.8 s** | **11.8 s** |

  一张卡一个 worker 时每个 worker 都是新程序、各自重付一次暖机，这项的收益归零（开关两边差 0.4 s，在噪声内）；
  每个 worker 依序转 2–3 张时才有 −0.8 s wall／−1.3 s CPU。注意最后两列：**worker=2 加这项的 wall 和
  4 个 worker 差不多，CPU 却少三分之一** —— 使用者的目标机是 16 GB，每个 worker 自己扛一份库与快取，
  所以 worker 数不是愈多愈好。要两项的收益叠加，就让 worker 数小于卡数、每人依序转好几张。

  **所以这项的收益随「每个 worker 分到的卡数」增加**：一人一张归零，一人 2–3 张约 −0.8 s wall，
  一人 10 张（21 角色场景、worker=2）约 −6 s。f-sceneload 在它的 worker 实测里确认了这个位置
  （`8bb19ca63`）：它量到的 `workers=2` → 21 角色 **58.0 s 里面已经含着这约 6 s**，没有这笔会是约 64 s。
  值得记一句**为什么预设刚好落在收益最大的点**：worker 多会削掉这项的舞台（一人一张时归零），
  而记忆体又不允许 worker 多（每个 ＋2.1 GB、第 5 个撞 16 GB），两个方向相反的约束从两头夹出 worker=2。
  不是巧合，调 worker 数的人要知道往哪一边动都会让这项变差。
- 转卡的次序迴归关卡：`Tools\ok_convert_order_check.lua`（小绯雪／Denia，2026-10-28 那个 bug）。动到
  `remake_ok_card` 的 view 身分、`with_zipmods_and`，或 `--oklib cards` 的 worker 配置，都要先跑它。
- ~~`library_zip_memo` 里 `|| crate::okstrict::active().is_some()` 这道闸门~~ **已处理（`d352dcb90`）**：
  整合 #15 后拿掉并重验，**量到零收益于是放回去**，见第二节最后一列。关卡
  `failed_remake_leaves_the_card_openable` 在改动版与放回版都 PASS；**跑它之前一定要设
  `OK_BASE_LIBRARY=<base_v1>`**，否则第一个 open 回 `r=1`、0.08 秒就在 `before` 那个 assert 挂掉，
  **看起来完全像回归其实是环境没设**（`configured_library()` 读那个变数，这句也补进了那条 `#[ignore]`）。

## 五、执行绪预算

这一轮动过执行绪的配置，三件事写在这里省掉下一个人误用。

### 改了什么

| 提交 | 改动 |
|---|---|
| `1a3a55dc2` | 全域 rayon 池从写死 `num_threads(MAX_THREADS)` 改成 `cpu_threads()`；`cpu_threads()` 除了 `OK_THREADS` 也读 `RAYON_NUM_THREADS` |
| `8fe9c24ab` | 17 支工具 bin 全部补上 `limit_threads()`（原本没有一支叫，各吃满这台机器的 32 条） |
| （待提交） | `cpu_threads()` 改成「环境变数明确给了就照给的，上限是硬件执行绪；没给才用 8」，具名池的硬上限跟着它 |

两个背景事实：`RAYON_NUM_THREADS` **从来没有生效过**（明确给了 thread count 的 rayon 池不会再读环境变数，
而写死的值刚好也是 8，所以没人发现）；而 `limit_threads()` 原本只有 `main.rs`（`ok-extract`）与 `ffi.rs`
（UE）叫，17 支工具一支都没叫。细节与防范在 [ERROR_LOG.md](ERROR_LOG.md) 的 2026-11-17 各条。

### 一、转卡／开卡这条路加宽执行绪几乎买不到东西

它是单执行绪与 IO 为主，加上 GPU 烘焙。f-sceneload 在同一张卡上交错三轮取中位数（`card-outfit`）：

| 一个行程拿到的执行绪 | wall 中位数 | CPU 中位数 |
|---|---:|---:|
| 8（不给 `[threads]`） | 5.01 s | 8.92 s |
| 4 | 5.15 s | 8.27 s |
| 2 | 5.30 s | 7.92 s |

8 → 2 条：wall 只多约 6%、CPU 省约 11%，峰值记忆体不随它变（2.34–2.38 GB）。

所以 **`cpu_threads()` 能被环境变数调高，价值完全落在批次工具那边**（`ok-lowpoly`、`ok-crowd-pack` 一次跑
几十张卡的离线工作），**不能拿转卡／开卡的数字替它背书**。这条路要快得靠「少做事」——共用树的暖机、少开
几次 session——不是靠多给执行绪；执行绪数在这里只是「守机器规矩的代价」那一面。

### 二、「批次工具慢 4 倍」是机制推估，没有量过

把工具从 32 条限回 8 条之后，我警告别组「可能接近 4 倍慢」。**那是从 32 ÷ 8 推的上限，不是量到的，
而且我自己手上的数据就反驳它**：同一个 bench 没有 `limit_threads()` 时拿满 32 条是 1172 ms、补上之后
8 条是 1298 ms，**只差约 10%**，而那段里本来就有一块宽 rayon 的逐 texel 工作（颜色遮罩烘焙）。这类工作离
线性扩展很远。

`ok-lowpoly` 本身**量不了**：它要 PNG 里有 portable snapshot（`okPv`），手上的 `CrowdAPNG/C001.png` 报
"PNG has no portable snapshot"，所以没有能喂给它的输入。要确定得用 C 组自己的卡与 `--budget` 实际跑一次。

**所以不要在任何地方留下「4 倍」这个数字当事实。** 正确的说法是：机制上确实变慢（32 → 8 条），幅度未量，
同类工作的唯一实测是约 10%。

### 三、这一节的数字本身就是「别用单趟去量」的例子

上面那张 8／4／2 的表，第一次只量了单趟，得到的是「8 条比 4 条快 **0.8 s**」，而且 4／2／1 三栏不单调
（4 条比 1 条还慢）——非单调就是噪声在主导的讯号。交错三轮取中位数之后，真正的差是 **0.29 s**，一半是噪声。

而且**跨时段的绝对值完全不能比**：单趟那次的绝对值是 6.5–7.4 s、交错那次是 5.0 s，差别不是改动造成的，
是前一次量的时候机器上有别组的全跑在吃资源。

被推翻的 0.8 s 刻意留在这里，不是只留正确答案——下一个人要知道的是**别再用单趟去量这件事**。
