## Context

現況動機見proposal。已觀察到：

- `StreetSocialCity`是Content專案，只有`CityLocalization`等插件內含C++ Runtime；沒有頂層Source。
- `Tools/street_city_resort_night_payload.lua`只提供Editor安裝／拍攝，將日光與月光切成固定日／夜兩態；不能當成遊戲日夜系統。
- 現行夜景：月光6lux、補光2.2lux、SkyLight倍率1.5、路燈2300lm、矮燈220lm；122+122座燈與1957個夜景Actor。月面已放大並程序著色，但位置固定。
- `DefaultEngine.ini`預設關閉AutoExposure；現有原生夜景相機另固定曝光。新增全天曝光時必須明確遷移這兩處，不能只旋轉DirectionalLight。
- 戶外programme有20個PK節點；D景點install／acceptance證明30模型、19分區及30盞既有景點燈。`city-plan.json`屬歷史規畫，不能直接當目前原生座標。
- 最近驗收地圖SHA為`af0f0e0553c3e5618ecbf78280401a5fe16d6364eafa2b7a916be04286f5fb36`，實作前仍需重讀當前檔案，不假設其他作業未更新。

## Goals / Non-Goals

**Goals:** 持續運行、可保存的日期／時鐘；真實日月方向與月相；美術可控的渡假村亮度；全部戶外景點與連接路線覆蓋；可量測的柔和反差。

**Non-Goals:** 本次規畫不落地改圖；首版不包含動態天氣、暴風雨、雲遮日月的氣象耦合、NPC營業AI或煙火活動邏輯。既有水面／煙火動態保留，新增燈光可以讀活動權重，但不能冒充活動已實作。

## Decisions

### 1. 單一Runtime控制權

新增獨立`StreetSocialCity/Plugins/CityEnvironment/` Runtime插件。時鐘狀態由GameInstance層持有、每個World只允許一個環境控制器；Editor可設定時刻，PIE與打包遊戲同樣運行。資料存於`/Game/UniversityCity/EnvironmentV1/`，包含日照曲線、夜景Profile、燈組註冊表及曝光設定。

擬提供`SetDateTime`、`SetHour`、`SetTimeScale`、`Pause`、`ResetPreview`與三語的簡單時間滑桿。0–24是預覽範圍，內部保存完整日期與UTC時間。預設真實60分鐘走完遊戲一天，倍速可調；時鐘用真實DeltaSeconds乘一次倍率，不再乘世界TimeDilation。Seek後直接計算狀態，鏡頭曝光另有穩定等待，不播放一整天事件。

替代方案：Python Tick只適合Editor驗證；直接掛多個Timeline會產生多個時鐘與跨日漂移，因此不採用。現有DaySequence為Experimental且會引入一套環境Actor集合，不直接替換目前整個天空。

### 2. 日月位置按天文資料，畫面亮度按美術控制

採用Astronomy Engine的C實作包入Runtime插件（實作階段固定commit、保留MIT授權，不在本規畫下載／安裝）。同一計算器輸出太陽與月亮的topocentric方位／高度、月相與亮側方向，避免手寫不完整的「月亮=太陽+180度」。另用UE SunPosition及預先保存的JPL Horizons樣本做獨立交叉驗證。

可修改的初始美術地理預設為北緯23.5、東經121、UTC+8、無夏令時間；這是虛構海灣城的規畫假設，不宣稱地圖實際位於該地。世界北向初值+X，透過已知方向標記校正。為保留大圓月，首個展示日期選「2026-10-22之後最近一次滿月所在本地日」，由天文計算器求值一次後保存；此後日期正常前進，不能每晚強制滿月。

太陽與月亮分別驅動Atmosphere Sun Light Index 0／1。直接照明依各自高度與遮蔽衰減，地平線下不可穿透地面照亮。月亮視直徑獨立美術參數，初值約5.5°，以目前6倍月亮實景校準；改為無視差的天空方向投影，月面、相位遮罩、光暈與實際月光共用方向，避免走到城另一端月亮大小／位置失真。關閉重複的原生月盤顯示，不能有兩個月亮。

天文位置準確不等於強迫真實黑夜：月光仍允許藝術增亮，夜間可讀補光具有獨立下限。無月／新月時，環境不能因月亮強度歸零而全黑。這一層不冒稱天文照度或建築採光認證。

### 3. 全天曲線與漸變

| 時段示意 | 天空／日月表現 | 公共路燈 | 景點／營業燈 |
|---|---|---|---|
| 00–04 | 深藍天空、月相及位置按日期，輪廓柔和可讀 | 夜間目標的60–75% | 休息區35–55%；關閉營業裝飾仍留引導 |
| 04–06 | 晨曦漸亮，星月淡出取決太陽高度 | 漸降 | 裝飾逐漸關閉 |
| 06–09 | 暖晨光、長陰影 | 太陽升高後關閉 | 保留必要室內與營業照明 |
| 09–16 | 清楚日光，日照方向連續移動 | 關閉 | 戶外裝飾關閉 |
| 16–18 | 金色夕陽與逐漸變冷的陰影 | 按暮光權重漸亮 | 重點景物提前低亮度亮起 |
| 18–20 | 藍調時刻，天空亮度持續下降 | 70–100% | 黃昏至夜晚的主要展示時段 |
| 20–23 | 明確夜色、月面可辨、路面連續可讀 | 100%的校準後目標 | 各區完整夜景，禁止過白光池 |
| 23–24 | 深夜漸弱，日期連續進到下一日 | 平滑轉為深夜值 | 非營業裝飾漸暗，公共動線不斷燈 |

上表時間是預覽安排，不是固定日出／日落。真正開燈權重由太陽高度從+3°到−8°的smoothstep決定，再乘營業／休息曲線；深夜值在遊戲時間約30分鐘內平滑收斂。日光與天空用連續曲線，夜燈每次相位變動按權重求值，避免閾值來回抖動。對正常播放平滑插值，對跳時直接求最終目標。

### 4. 夜間先調平反差，再加景點燈

現有2300lm路燈與220lm矮燈是參考，不沿用為所有景點通用值。先在商店街、飯店庭院、湖畔三種樣本上A/B：路燈試850–1400lm、矮燈100–160lm；重點是低眩光、較寬的柔和配光和遮光。將少量明暗補償分散到天空／漫射環境，不以把全城照亮成白晝來換取可讀性。現行6lux／2.2lux／1.5作為夜景基線，初次試驗只將補光小幅調至2.4，不能同時任意提高全部光源。

白天可用30,000–80,000lux的日光量級搭配EV100範圍校準；不能把舊6lux人造白天當成物理日照。夜晚的藝術月光與環境下限則明確分層。記錄實際LightUnits，禁止把SkyLight倍率、流明與lux混成同一數字比較。

夜間曝光起始探索範圍EV100 −1至3，日間10至15，最後以灰卡與實景校準曲線取代大範圍自由適應。啟用受管理的PostProcessVolume與一致EV100語義；檢查並移除正式拍攝相機上遺留的固定曝光覆寫。使用中央／人物區域測光遮罩降低月亮與招牌對曝光的牽引。Local Exposure只做輕度高光／暗部保留，不能用它補救不合格的原始HDR反差。室內外轉換約1–3真實秒穩定，不隨遊戲倍速瞬間閃變。

### 5. 景點以場所分層，不靠堆光源

逐ID方案見[outdoor-lighting-plan.md](outdoor-lighting-plan.md)，80個來源識別碼與座標來源見[coverage.json](coverage.json)。每區使用「環境基底、通路引導、景物重點、人物停留」四層；可共用路燈或相鄰洗光，但每個景點都需獨立入鏡確認。先接管D景點現有30盞燈、活動燈、街燈及招牌，停用重複控制，再補缺口。

景物光禁止純白過曝，樹冠不整片染色，水景不蓋住錦鯉；山景／海灣保留暗遠景，人物交談與前景步道維持柔和底光。夜市和運動場有自己的營業／活動Profile，公共路線不受收攤關燈影響。

### 6. 資料、效能與更新

一次建立Actor／Component註冊表，不每幀掃描全世界；新增／卸載區域增量註冊。資料欄位包含ID、sourceActor、zone、group、Kelvin、目標流明、照射方向／半徑、遮光、陰影等級、開燈曲線、深夜下限、相機與淨空資料。

時鐘／光照狀態以10Hz求值，方向每幀插值；SkyLight使用引擎可時間切片的更新路徑並限制頻率，不逐幀同步RecaptureSky。MPC控制既有SignNightStrength與發光燈芯，關燈時燈芯也同步淡出；若目前材質參數屬MI而非MPC，增加共用乘數，不複製122份材質圖。舊Lua安裝／拍攝的固定intensity assert改為核對Profile與時刻求值，避免把Runtime誤判成資產遭改動。

局部燈依可見性／距離分級，遠處主要保留發光外觀。初始預算：1080p主要角色視角最多48個顯著局部燈、最多8個局部陰影燈，兩個天體直接光在地平線交接時可並存但不雙倍全亮；燈具HISM／ISM依共享網格材質合批。以當前同機器同畫質為基線，新增夜景GPU時間目標≤2ms、總幀時間增加≤15%；這些是實作預算，尚未量測，不宣稱已達60fps。

### 7. 驗收矩陣

- 全城狀態每整點0–23一份，額外測23:59:59→次日00:00:00。六個代表鏡位（商店街、湖畔、河岸、海灣、庭院、夜市）各拍24整點，共144組HDR+LDR。
- 80個景點ID各在藍調入夜、21:00、02:00有有效角色視角，可共享相同畫面，但對應ROI必須包含該景物、人物／通路及其相鄰環境；另驗收每條連接路線。
- 春分、夏至、秋分、冬至、新月、上弦、滿月、下弦做幾何／相位與日期測試；所有天文樣本統一UTC、北向、topocentric與折射定義。
- 從線性HDR／灰卡取反差，不用經tone-map後的sRGB像素冒稱lux。路徑≤3:1、景物≤4:1，地面P10/P50≥0.20；LDR步道／景物ROI的99%非發光像素不裁切，且夜間同一灰卡中位亮度目標為白天25–55%。先比靜止穩定曝光，再錄行走曝光適應。
- 原生相機需檢查是否位於室內、牆內或看不到目標；沿用既有LI鏡位的失敗經驗，數值亮度通過不代表鏡位通過。
- 每個保存階段SHA前置比對、exact備份、fresh run_id；另程序重開、PIE及打包遊戲驗證，真實記錄退出碼與限制。非零退出不得改成通過。

## Risks / Trade-offs

- [物理月光太暗或無月] → 真實方向／月相保留，另設不依賴月亮的藝術補光下限；不得製造第二個亮月亮。
- [提高曝光把晚上拉成白天] → 夜／日曝光曲線有界、以灰卡及天空輪廓對比驗收，先降低局部燈。
- [既有光源與新光源疊加] → 先建立完整分類註冊表，原室內光不盲目調整；明確記錄每個原LightComponent控制權。
- [大月亮投影和水面反射方向錯誤] → 共用天體方向、無視差天空投影，月盤、Halo與水面反射同時拍攝驗收。
- [曆表第三方依賴／跨平台建置] → Runtime封裝固定版本C來源，保留授權和reference樣本；不在遊戲執行時連網計算。
- [大量動態燈及SkyLight更新成本] → 距離分級、少量局部陰影、共享實例燈具、限制重捕捉，記錄Profiler數據。
- [舊工具再次把世界切回固定夜景] → 安裝器與驗收器同步遷移，固定月夜保留為停用Runtime時的明確備援Profile。

## Migration Plan

使用者在實作開始時明確追加z-fighting修正。增加原生LOD網格與實例變換匯出、獨立共面／近平行重疊三角形掃描、逐項修正與近遠斜角移動拍攝。原始資料保持規則的例外只限已確認的深度衝突，必須寫出修正前後與恢復清單；不更動樓層／室內用途，不用全域PixelDepthOffset掩蓋。月面與Halo分開深度層、裝飾與水面有實體間隔，共享同一時間控制。

先建立唯讀基線及完整燈表→完成時鐘／天文與三個樣區→反差合格後展開全50景點與路線→遷移曝光及舊工具→原生、PIE與打包驗收。每步保存新增控制資料與目前原LightComponent的值；回復時解除新控制器並恢復這些值，不用舊整圖覆蓋較新的共用地圖。跨聊天仍不傳訊息，等待檔案釋放並用SHA前置條件保護保存。
